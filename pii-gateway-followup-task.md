# Задача для AI в репозитории `api.vega.chat`: доработки шлюза по итогам клиентской части officevega

Клиент (репозиторий `getoffice`, officevega) реализовал ваш `pii-getoffice-client-task.md`
(заголовок `X-Vega-Session`, разбор `pii_shield_error`, индикатор щита). При ревизии клиента
нашлись две вещи, которые надо сделать на стороне шлюза. Продукт ещё не в проде, реальных
пользователей и «старых» ключей нет, обратную совместимость поддерживать не нужно.

## 1. Клиент теперь идентифицирует себя как `officevega` (переименование)

Раньше клиент слал `client_id = "vegaoffice"`, ключ `name = "vegaoffice"` и ходил на
`/api/v1/keys/vegaoffice`. Теперь везде **`officevega`**:

| Что | Было | Стало (шлёт клиент) |
|---|---|---|
| OAuth device flow `POST /api/auth/device/code` | `{"client_id":"vegaoffice"}` | `{"client_id":"officevega"}` |
| Выпуск ключа | `POST /api/v1/keys/vegaoffice`, тело `{"name":"vegaoffice"}` | `POST /api/v1/keys/officevega`, тело `{"name":"officevega"}` |
| Отзыв ключа при выходе | `POST /api/v1/keys/vegaoffice/revoke` | `POST /api/v1/keys/officevega/revoke` |

Что сделать на сервере:
1. Зарегистрировать `client_id = "officevega"` в whitelist device-flow (иначе `400 invalid_client`).
2. Обслуживать `/api/v1/keys/officevega` и `/api/v1/keys/officevega/revoke`.
   Ключ создаётся под именем `officevega` (именно по этому имени включается PII-щит),
   прежнее поведение «удалить прежний ключ этого имени при выпуске нового» сохранить.
3. Старые имена (`vegaoffice`, `getoffice`, `genoffice`) можно вообще убрать из whitelist
   или оставить как алиасы, выдающие ключ `officevega`. Пользователей нет, выбирайте что проще.
4. Проверить: после входа из приложения ключ в БД называется `officevega`, и запросы с ним
   действительно проходят через PII-щит (тот же curl из раздела 5 прошлой инструкции).

## 2. Незащищённый маршрут `POST /api/alpha/decisions` (утечка ПДн, важно)

В клиенте включён по умолчанию **поиск по файлам с реранком** (`apps/shell/src/main/file-index/jev.ts`,
`rerank.ts`). Для каждого поискового запроса пользователя клиент отправляет **фрагменты
локально проиндексированных документов** на `https://api.vega.chat/api/alpha/decisions`
(модель `typesafe/jev-router`, дальше запрос уходит во внешний сервис TypeSafe/OpenRouter).
Этот маршрут не входит в список защищённых (`chat/completions`, `responses`, `messages`,
`completions`, `embeddings`, `images`), поэтому ПДн из файлов пользователя сейчас уходят
наружу без обезличивания. Это нужно закрыть тем же щитом.

### Формат запроса (что шлёт клиент)

`Authorization: Bearer <ключ officevega>`, `X-Vega-Session: <uuid, новый на каждый запрос>`.

```json
{
  "model": "typesafe/jev-router",
  "state": {
    "query": "поисковая фраза пользователя (до 512 символов)",
    "documents": [
      { "title": "имя файла/название (до 128 симв.)",
        "heading": "заголовок раздела (до 128 симв.)",
        "text": "фрагмент текста документа (до 1200 симв.)" }
    ]
  },
  "questions": { "d0": { "type": "score", "instructions": "...", "criteria": ["..."] } },
  "provider": { "only": ["typesafe"], "allow_fallbacks": false, "zdr": true, "data_collection": "deny" }
}
```

До 20 документов, тело до 24 КБ. Ответ содержит только числовые оценки 0–2 по документам
(вероятности и usage), **значений ПДн в ответе нет, обратная подстановка (restore) не нужна.**

### Что сделать в шлюзе

1. Добавить `/api/alpha/decisions` в список маршрутов под щитом для ключей `officevega`
   (так же, как остальные).
2. Обезличивать строковые значения: `state.query`, `state.documents[*].title`,
   `state.documents[*].heading`, `state.documents[*].text`. Поля `model`, `questions`,
   `provider` не трогать (там нет ПДн, а `instructions`/`criteria` должны остаться дословно).
   Структуру и порядок `documents` сохранять: клиент сопоставляет оценки по индексу.
3. Сессия: клиент шлёт новый `X-Vega-Session` на каждый запрос, словарь токенов не нужно
   переиспользовать между запросами. Внутри одного запроса один и тот же человек = один
   токен во всех документах.
4. Fail-closed: при недоступности сервиса защиты вернуть `503` с телом
   `{"error":{"code":"pii_unavailable","message":"...","type":"pii_shield_error"}}`.
   Клиент в этом случае просто сохраняет локальный порядок результатов (без ошибки в UI),
   ничего наружу не уходит.
5. Ограничение по времени: у клиента таймаут на этот запрос ~4 с (`TIMEOUT_MS = 4000` в
   `jev.ts`). Обезличивание 20 фрагментов по 1200 символов должно укладываться в ~1–2 с
   (одним батчем `anonymize-text`, кэш по хешу). Если это невозможно, лучше вернуть быстро
   `503`, чем задерживать: поиск по файлам должен оставаться быстрым. Сообщите, если нужно
   увеличить таймаут на клиенте.
6. Качество: имена файлов (`title`) часто содержат ФИО («Договор Иванов И.И.docx»),
   не пропускайте их без обезличивания.
7. Не логировать тела запросов и ответов.
8. Другие endpoints реранка в клиенте (`openrouter`, `direct`) идут мимо вашего шлюза,
   их не трогаем: это явный выбор пользователя со своим ключом.

### Критерии приёмки

1. Запрос на `/api/alpha/decisions` с ключом `officevega`, где в `state.documents[*].text`
   есть ФИО, телефон и паспорт, а в `title` ФИО: в исходящем к внешней модели payload только
   токены, поля `questions`/`provider`/`model` без изменений.
2. Ответ приходит клиенту без изменений формата (оценки по индексам документов).
3. `pm2 stop pii-service` даёт `503 pii_unavailable`, ничего наружу не уходит.
4. Запрос с ключом другого имени (не `officevega`) щитом не затрагивается (как и раньше).
5. Задержка добавки щита для типичного запроса (20 документов) не более ~1–2 с.

## 3. Веб-поиск не трогаем

Веб-поиск клиента (`chat/completions` с плагином `web`, поисковая фраза пользователя в
`messages[0].content`) остаётся как есть: по решению продукта он проходит через общий
щит по обычным правилам без специальных исключений и доработок.
Заголовок `X-Vega-Session` для него клиент не ставит, шлюз выводит сессию сам (это
допустимо: запрос одиночный, обратная подстановка в ответ поиска не критична).

## 4. Что клиент уже сделал (для справки, менять не нужно)

- `X-Vega-Session` на всех запросах к `api.vega.chat` (чат: стабильный id разговора; медиа и
  прочее: uuid на запрос).
- Разбор `pii_shield_error`: сообщение шлюза показывается пользователю. `503 pii_unavailable`
  повторяется 2 раза (1,5 с и 3 с), `400`/`413`/`422` не повторяются.
- Индикатор щита (иконка с подсказкой) в панели AI всех приложений.
- Переименование identity в `officevega` (раздел 1).
