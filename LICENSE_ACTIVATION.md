# Активация программы и проверка лицензионного ключа

Документ для разработки функции активации в приложении «Офис ВЕГА» и на сервере officevega.com.
Он написан так, чтобы его можно было целиком передать AI-ассистенту как контекст.

Разделы помечены:
- **[Есть]** — уже реализовано в репозитории.
- **[Предложение]** — нужно реализовать, здесь описан рекомендуемый контракт.

---

## 1. Что уже есть [Есть]

Покупка, выдача ключей, письма и дашборд готовы. Эндпоинта активации и проверки ключа **пока нет**.

### Формат ключа

```
XXXXX-XXXXX-XXXXX-XXXXX-XXXXX
```

- 25 символов из алфавита `ABCDEFGHJKLMNPQRSTUVWXYZ23456789` (без `0/O/1/I`), 125 бит энтропии.
- Генерация: `generateLicenseKey()` в `lib/licensing/keys.ts` (`crypto.randomBytes`).
- Нормализация: `normalizeLicenseKey(key)` убирает пробелы и дефисы и приводит к верхнему регистру.
  Пользователь может вводить ключ в любом регистре, с дефисами или без.
- Хеш: `hashLicenseKey(key)` = SHA-256 от нормализованного ключа, hex.
  **В БД хранится только хеш.** Исходный ключ восстановить нельзя.

### Таблицы (миграции `db/migrations/001_licensing.sql`, `002_auth.sql`)

```
users ─┬─ account_members ── accounts (individual | company)
       │                        │
       └─ seats.assigned_user_id│
                                ├─ orders ── entitlements (seats, starts_at, expires_at, status)
                                              └─ seats ── license_keys (key_hash, status)
```

Поля `license_keys`:

| Поле | Смысл |
|---|---|
| `id` | UUID ключа |
| `seat_id` | место, к которому привязан ключ |
| `key_hash` | SHA-256 нормализованного ключа, уникален |
| `key_hint` | последние 4 символа (для поддержки и дашборда) |
| `status` | `active` или `revoked` |
| `encrypted_key` | зашифрованный ключ до отправки письма, после отправки `NULL` |
| `issued_at`, `delivered_at`, `revoked_at` | временные метки |

Инварианты:
- На одном месте (`seat`) не более одного ключа со статусом `active`.
- Перевыпуск (`issueKeyForSeat`) отзывает старый ключ и создаёт новый.
- Освобождение места (`releaseSeat`) отзывает ключ.
- Срок действия хранится в `entitlements.expires_at`, а не в ключе.

### Когда ключ считается действительным [Есть, логика описана, кода проверки нет]

Ключ действителен, только если выполняются **все** условия:

1. найден `license_keys` с `key_hash = hashLicenseKey(input)`;
2. `license_keys.status = 'active'`;
3. у места есть держатель: `seats.assigned_user_id IS NOT NULL`;
4. `entitlements.status = 'active'`;
5. `entitlements.expires_at > now()`.

Эталонный запрос:

```sql
SELECT k.id            AS key_id,
       k.seat_id,
       s.assigned_user_id,
       u.email,
       e.id            AS entitlement_id,
       e.expires_at,
       a.type          AS account_type
FROM license_keys k
JOIN seats s         ON s.id = k.seat_id
JOIN entitlements e  ON e.id = s.entitlement_id
JOIN accounts a      ON a.id = s.account_id
JOIN users u         ON u.id = s.assigned_user_id
WHERE k.key_hash = $1
  AND k.status = 'active'
  AND e.status = 'active'
  AND e.expires_at > now();
```

`JOIN users` без `LEFT` сразу отсекает места без держателя. Всё, что не нашлось, для клиента одинаково: «ключ недействителен».

## 2. Что нужно сделать [Предложение]

### 2.1. Активация, привязка к устройству и проверка

Минимальный вариант «только проверка ключа» хуже: один ключ можно раздать неограниченному числу людей.
Рекомендуется привязка к устройствам с лимитом.

Новая миграция `db/migrations/003_activations.sql`:

```sql
CREATE TABLE license_activations (
  id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  license_key_id  UUID NOT NULL REFERENCES license_keys(id) ON DELETE CASCADE,
  device_hash     TEXT NOT NULL,          -- SHA-256 от device_id, присланного приложением
  device_name     TEXT,                   -- «MacBook Ивана», для списка в дашборде
  app_version     TEXT,
  first_seen_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
  last_seen_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
  revoked_at      TIMESTAMPTZ,
  UNIQUE (license_key_id, device_hash)
);
CREATE INDEX license_activations_key_idx ON license_activations (license_key_id);
```

Лимит устройств на ключ: константа `MAX_DEVICES_PER_KEY` (рекомендуется 2 или 3, решает владелец продукта).
Считаются активации с `revoked_at IS NULL`.

### 2.2. Контракт API

Все эндпоинты: `POST`, JSON, `Content-Type: application/json`, ответ `Cache-Control: no-store`.
Маршруты: `app/api/license/activate/route.ts`, `validate/route.ts`, `deactivate/route.ts`.

**`POST /api/license/activate`**

Запрос:

```json
{
  "key": "ABCDE-FGHJK-LMNPQ-RSTUV-23456",
  "deviceId": "стабильный идентификатор установки, >= 16 символов",
  "deviceName": "MacBook Ивана",
  "appVersion": "1.4.0"
}
```

Успех, `200`:

```json
{
  "ok": true,
  "license": {
    "expiresAt": "2027-09-30T21:00:00.000Z",
    "accountType": "individual",
    "holderEmail": "user@example.com"
  },
  "token": "<подписанный токен, см. 2.3>",
  "refreshAfter": "2026-10-02T12:00:00.000Z"
}
```

Ошибка: `{"ok": false, "code": "<код>", "message": "<текст для пользователя>"}`.

| HTTP | `code` | Когда |
|---|---|---|
| 400 | `bad_request` | нет или неверный формат полей |
| 404 | `invalid_key` | ключ не найден или не `active` (не различать причины) |
| 403 | `expired` | срок `entitlements.expires_at` истёк |
| 403 | `device_limit` | достигнут `MAX_DEVICES_PER_KEY`, новая активация невозможна |
| 429 | `rate_limited` | слишком много запросов |
| 500 | `server_error` | внутренняя ошибка |

Разделять `invalid_key` и `revoked` не нужно: так по ответу нельзя узнать, существовал ли ключ.
Для `expired` разделение допустимо: ключ уже прошёл проверку, значит его знает владелец.
Поэтому `expired` возвращайте только если ключ найден и `active`.

Логика: в одной транзакции найти ключ (запрос выше, но без условия по сроку, срок проверить отдельно),
заблокировать строку ключа `FOR UPDATE`, посчитать активные устройства, вставить активацию
`ON CONFLICT (license_key_id, device_hash) DO UPDATE SET last_seen_at = now(), revoked_at = NULL`
(повторная активация на том же устройстве не расходует лимит).

**`POST /api/license/validate`**

Та же пара `key` + `deviceId`. Не создаёт новую активацию: если устройство не активировано, вернуть `404 not_activated`.
Обновляет `last_seen_at`, возвращает свежий `token` и `expiresAt`.
Приложение вызывает его раз в сутки при наличии сети.

**`POST /api/license/deactivate`**

`key` + `deviceId`. Ставит `revoked_at = now()` у активации и освобождает слот устройства.
Нужен для кнопки «Выйти из лицензии» в приложении и для переноса на другой компьютер.

### 2.3. Подписанный токен для офлайн-работы

Офисная программа должна работать без сети. Для этого сервер подписывает ответ, а приложение проверяет подпись встроенным публичным ключом.

- Алгоритм: **Ed25519** (`crypto.sign(null, data, privateKey)` в Node).
- Приватный ключ: переменная окружения `LICENSE_SIGNING_PRIVATE_KEY` (PEM или base64 PKCS8). Только на сервере, не в репозитории, не в клиенте.
- Публичный ключ вшивается в приложение. Сделайте его ротируемым: в токене поле `kid`.
- Генерация пары: `node -e "const {generateKeyPairSync}=require('crypto');const k=generateKeyPairSync('ed25519');console.log(k.privateKey.export({type:'pkcs8',format:'pem'}));console.log(k.publicKey.export({type:'spki',format:'pem'}))"`.

Полезная нагрузка токена (JSON, затем base64url, затем подпись):

```json
{
  "v": 1,
  "kid": "2026-10",
  "keyId": "<license_keys.id>",
  "device": "<device_hash>",
  "exp": "<entitlements.expires_at, ISO>",
  "iat": "<когда выдан>",
  "graceUntil": "<iat + 14 дней>"
}
```

Поведение приложения:
1. Проверить подпись и совпадение `device` с собственным `deviceId`.
2. Если `now < exp` и `now < graceUntil` — работать.
3. Раз в сутки вызывать `/validate`. При успехе заменить токен.
4. Если сети нет — работать до `graceUntil`. Если `/validate` вернул `invalid_key` или `expired`, сразу закрыть доступ и удалить токен.
5. Часы ОС менять можно, поэтому хранить последнюю известную серверную дату и не принимать время раньше неё.

### 2.4. Идентификатор устройства

- `deviceId` создаёт приложение при первом запуске (UUID v4) и хранит в защищённом хранилище ОС (Keychain, Credential Manager, libsecret).
- Сервер хранит только `SHA-256(deviceId)`.
- Не использовать серийные номера и MAC-адреса: это персональные данные и лишняя зависимость от железа.

## 3. Безопасность

- **Ключ в логах.** Не логировать тело запросов активации и сам ключ. В `console.error` передавать только код ошибки и `keyId`.
- **Сравнение.** Искать по `key_hash` через индекс. Поскольку ключ высокоэнтропийный, отдельное constant-time сравнение не нужно.
- **Rate limit** на `activate`/`validate`: по IP и по `key_hash`. Рекомендуется 10 запросов в минуту на IP и 30 в час на ключ. Заголовок IP берётся из `x-forwarded-for` (nginx его выставляет).
- **Защита от перебора.** Ключ 125 бит, перебор нереален, но ограничение по IP всё равно нужно, чтобы не нагружать БД.
- **Единый ответ** для несуществующего, отозванного и принадлежащего чужому месту ключа: `invalid_key`.
- **Только HTTPS.** Приложение должно отказываться работать по `http://`. Рекомендуется закрепить (pinning) публичный ключ подписи, а не сертификат.
- **Не доверять клиенту.** Решение о валидности принимает сервер. Токен лишь кэш этого решения.
- **Секреты** (`LICENSE_SIGNING_PRIVATE_KEY`, `LICENSE_ENCRYPTION_KEY`) не выносить во frontend и не коммитить.
- `LICENSE_ENCRYPTION_KEY` нужен только для писем с ключами. Потеря этого значения делает нерасшифровываемыми ключи, которые ещё не отправлены.

## 4. Связь с дашбордом

Что должно происходить на сервере при действиях в дашборде:

| Действие в дашборде | Эффект на активацию |
|---|---|
| Освободить место | ключ `revoked`, при следующем `/validate` приложение получит `invalid_key` |
| Перевыпустить ключ | старый ключ `revoked`, активации старого ключа перестают проходить, пользователь вводит новый ключ |
| Срок истёк | `/validate` вернёт `expired`, приложение работает только до `graceUntil` |
| Компания снимает админа | на активацию не влияет |

Рекомендуется добавить в дашборд список устройств ключа (из `license_activations`) и кнопку «Отключить устройство» (`revoked_at = now()`), чтобы сотрудник не упирался в `device_limit` после смены компьютера.
Это потребует расширить `getDashboard` в `lib/licensing/dashboard.ts` и добавить серверное действие с проверкой прав, как у `releaseSeat`.

## 5. Как реализовывать в этом репозитории

Соглашения проекта:
- Next.js 16, TypeScript, **pnpm** (вместо `npx` — `pnpm dlx`). Тесты: `pnpm test` (встроенный `node:test`, без зависимостей). Проверка типов: `pnpm typecheck`.
- Код в `lib/licensing/*.ts` импортирует соседние модули **относительными путями с расширением `.ts`** (например, `./keys.ts`), без алиаса `@/`. Так его можно запускать из Node без сборки (воркер, тесты). Алиас `@/` допустим только в `app/` и `components/`.
- Бизнес-логику вынести в `lib/licensing/activation.ts` (функции принимают `TxRunner`/`Db`), а route-файлы оставить тонкими, как `app/api/robokassa/success/route.ts`.
- Любые изменения БД — только новым файлом `db/migrations/00N_*.sql`, применение `pnpm db:migrate`. Старые миграции не править.
- Тесты БД используют `createTestDb()` из `tests/helpers.ts` (временная схема, удаляется после прогона).

Рекомендуемый порядок:
1. Миграция `003_activations.sql`.
2. `lib/licensing/activation.ts`: `activate()`, `validate()`, `deactivate()`, `signLicenseToken()`.
3. Три route-файла и rate limit.
4. Тесты (список ниже).
5. Серверная часть списка устройств в дашборде.
6. Клиент (приложение): ввод ключа, хранение токена, ежедневная проверка, режим офлайн.

## 6. Критерии приёмки и тесты

Тесты сервера (`tests/activation.test.ts`):
- корректный ключ активируется, возвращает токен с верной подписью и `exp`, равным `expires_at`;
- ключ в нижнем регистре и без дефисов принимается;
- несуществующий ключ: `404 invalid_key`;
- отозванный после перевыпуска старый ключ: `404 invalid_key`, новый работает;
- освобождённое место: ключ перестаёт работать;
- истёкший `entitlement`: `403 expired`;
- ключ места без держателя недействителен;
- третье устройство при лимите 2: `403 device_limit`; повторная активация того же устройства лимит не тратит;
- `deactivate` освобождает слот, после него можно активировать новое устройство;
- параллельные активации двух разных устройств при лимите 1: проходит ровно одна;
- в логах и ответах нет открытого ключа;
- токен с изменённой нагрузкой не проходит проверку подписи.

Проверка вручную:
1. Купить тестовую лицензию, получить ключ из письма.
2. Активировать приложение, отключить сеть, убедиться, что оно работает.
3. В дашборде перевыпустить ключ, включить сеть, убедиться, что приложение закрыло доступ после `/validate`.
4. Ввести новый ключ и убедиться, что работа восстановилась.

## 7. Открытые вопросы к владельцу продукта

Перед реализацией стоит решить:
- Сколько устройств допускается на один ключ (2 или 3)?
- Какой срок офлайн-работы (`graceUntil`): 7 или 14 дней?
- Нужен ли режим без интернета вообще, или приложение проверяет ключ при каждом запуске?
- Что делать с пробным периодом: отдельный тип ключа или работа без ключа с ограничениями?
- Нужно ли показывать в приложении имя держателя и срок (`holderEmail`, `expiresAt`)?
