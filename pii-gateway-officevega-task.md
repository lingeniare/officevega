# Задача: анонимизация ПДн в трафике officevega на шлюзе api.vega.chat

Документ — ТЗ для AI/разработчика, дорабатывающего сервер api.vega.chat (ВЕГА провайдер).
Контекст: 152-ФЗ, запрет трансграничной передачи ПДн. Персональные данные из
документов пользователя не должны попадать во внешние LLM (OpenRouter и т.д.).

Связанные документы: `pii-anonymization-changes.md` (что уже сделано в ru.vega.chat),
`pii-service-integration.md` (контракт локального `pii-service`).

## 1. Текущее состояние

- Локальный `pii-service` (Python, FastAPI, `127.0.0.1:8787`, заголовок `x-pii-token`)
  уже обезличивает файлы и текст: `POST /v1/anonymize-file`, `POST /v1/anonymize-text`,
  `GET /health`. Токены вида `#PERSON_1#`, значения ПДн не логируются и не возвращаются.
- В ru.vega.chat защита встроена в маршрут `app/api/search` и покрывает только
  файлы, загруженные в веб-чат.
- **Трафик officevega (десктоп-приложение: docs, sheets, slides, html, markdown, pdf,
  CLI, MCP) идёт на `https://api.vega.chat/api/v1` и защитой НЕ покрыт.**

## 2. Что именно шлёт officevega на api.vega.chat

Стандартный OpenAI-совместимый `POST /api/v1/chat/completions` (stream SSE, tools):

| Часть запроса | Содержимое | Риск ПДн |
|---|---|---|
| `messages[role=system]` | системный промпт, иногда фрагменты документа | да |
| `messages[role=user].content` (string или массив частей) | текст пользователя | да |
| `messages[role=user].content[].image_url` | `data:image/...;base64,...` (вставленные/прикреплённые картинки) | да (OCR) |
| `messages[role=tool].content` | **результаты инструментов: текст документа, ячейки, слайды** — основной канал утечки | да |
| `messages[role=assistant].tool_calls[].function.arguments` | JSON-аргументы правок документа (`str_replace`, `apply_ops` и т.п.) | да |
| media-анализ: `image_url`, `video_url` (data URL) | картинки/видео | да |

Файловых частей (`type:"file"`, PDF base64) в чат-запросах officevega нет.
Также есть эндпоинты `/images`, веб-поиск (plugin `web`), `/models`.

## 3. Целевая архитектура

```
officevega --HTTPS--> api.vega.chat (шлюз)
                         |-- anonymize (текст/картинки) --> pii-service 127.0.0.1:8787
                         |-- словарь токенов на сессию (память/Redis, TTL)
                         v
                      OpenRouter (только обезличенные данные)
                         |
                      ответ (SSE / JSON) <-- ДЕ-анонимизация (restore) в шлюзе
                         v
                      officevega (получает реальные значения)
```

Принципы:
1. **Fail-closed**: любая ошибка/таймаут `pii-service` = ошибка клиенту, запрос наружу
   не уходит. Никакого fallback «отправить как есть».
2. **Обратимость**: модель видит токены, но пользователь и документ должны получать
   реальные значения. Иначе правки документа ломаются (агент вернёт операции с
   `#PERSON_1#` вместо ФИО).
3. **Стабильность токенов между запросами сессии**: один и тот же человек/номер = один
   токен во всех ходах агентного цикла.
4. Маппинг токен↔значение хранится только на нашем российском сервере, в памяти/Redis
   с TTL, не пишется в логи и на диск в открытом виде.

## 4. Изменения в `pii-service`

1. Добавить в оба эндпоинта необязательный параметр `session_id` (multipart-поле /
   JSON-поле). Пока `session_id` тот же, нумерация `#TYPE_N#` и словарь значений
   продолжаются (одинаковое значение → тот же токен).
2. Хранилище сессий: `dict` с TTL (например 2 часа скользящий) и лимитом размера;
   при росте нагрузки — Redis. Ключ — `session_id` (привязать к API-ключу клиента, чтобы
   сессии разных пользователей не пересекались: `hash(api_key)+session_id`).
3. Новый эндпоинт `POST /v1/restore-text` — JSON `{ "session_id", "text" }` →
   `{ "text" }` с подстановкой токенов обратно. Требования:
   - точная замена `#TYPE_N#` (регэксп `#[A-Z_]+_\d+#`), неизвестные токены оставлять как есть;
   - в русских падежах восстанавливается каноническое значение (допустимо; отметить
     ограничение);
   - вызов только по токену `x-pii-token`, значения ПДн в логи не попадают.
4. Опционально `POST /v1/session/close` (`{session_id}`) — явная очистка.
5. Кэш результата анонимизации по `sha256(text)+session_id` (TTL 15 мин), потому что
   агентный цикл повторно шлёт весь контекст на каждом ходу.
6. Производительность: несколько воркеров uvicorn (`ecosystem.config.js`), таймаут
   клиента ≥ 120 с для файлов, для чата — короче (≈ 5–10 с на сообщение).
7. Тесты (pytest): стабильность токенов между вызовами с одним `session_id`, изоляция
   разных сессий, restore, неизвестные токены, TTL, отсутствие значений ПДн в логах.

## 5. Изменения в шлюзе api.vega.chat

### 5.1. Идентификация сессии
- Читать заголовок `X-Vega-Session` (его начнёт присылать officevega, см. раздел 6).
  Если заголовка нет — сессия = хеш `(api_key, hash первого user-сообщения)`, либо
  одноразовая сессия на запрос (тогда нумерация не сквозная — допустимо для старых клиентов).

### 5.2. Обработка запроса `chat/completions` (до пересылки в OpenRouter)
Для каждого сообщения в `messages`:
- `content` — строка → `anonymize-text`;
- `content` — массив частей: `type:"text"` → `anonymize-text`;
  `image_url` (data URL/URL) → скачать/декодировать → `anonymize-file` (OCR rus+eng);
  результат — текст, заменяющий картинку (`[Изображение, текст: ...]`). Если
  `warnings` содержит `no_text` (фото без текста) → отклонить запрос с понятной
  ошибкой (или заметка вместо картинки — по политике);
  `video_url`, `input_audio`, `file` → отклонять/заменять заметкой
  («вложения этого типа не поддерживаются в режиме защиты ПДн»);
- `role:"tool"` и `role:"system"` — как текст (обязательно; это основной канал);
- `role:"assistant"`:
  - `content` — как текст;
  - `tool_calls[].function.arguments` — это JSON-строка: анонимизировать **строковые
    значения внутри JSON**, сохраняя валидность JSON (парсить → обходить → собирать
    обратно). Иначе история с реальными ПДн уйдёт наружу.
- Использовать один `session_id` на весь запрос; результаты кэшировать по хешу.
- Ограничения: объём/число вызовов, параллельная обработка сообщений с пулом.

Применять защиту ко всем маршрутам, где шлюз пересылает пользовательские данные
наружу: `chat/completions`, `/images` (prompt), plugin `web` (поисковый запрос),
`embeddings`, `responses`, если есть. Список исключений (если нужны) — явно
задокументировать. `/models` и подобное не затрагиваются.

### 5.3. Обработка ответа (restore)
- **Не-потоковый JSON**: пройти `choices[].message.content` и
  `tool_calls[].function.arguments` (строка JSON: заменять токены внутри строковых
  значений, сохраняя валидность JSON) → `restore-text`.
- **SSE-поток** (основной случай officevega):
  - буферизовать `delta.content` и `delta.tool_calls[].function.arguments` по индексу;
  - токен `#TYPE_N#` может быть разорван границей чанков: держать в буфере хвост,
    начиная с последнего незакрытого `#` (макс. длина токена ~ 32 символа); отправлять
    клиенту только «безопасный» префикс, остаток — при следующем чанке или в конце потока;
  - для `reasoning`/`reasoning_content` — то же, либо вырезать;
  - не менять структуру SSE (`data: {...}`, `[DONE]`), `usage`, `finish_reason`.
  - restore выполнять локально через словарь сессии (в самом шлюзе/через
    `restore-text`), не по сетевому вызову на каждый чанк.
- В экранированных JSON-строках значения ПДн подставлять с корректным JSON-экранированием
  (кавычки, переводы строк).

### 5.4. Ошибки клиенту
| Ситуация | Ответ |
|---|---|
| `pii-service` недоступен/таймаут | `503`, `{"error":{"code":"pii_unavailable"}}` |
| фото без текста | `422`, `code: "pii_image_no_text"` |
| неподдерживаемое вложение (видео/аудио) | `400`, `code: "pii_attachment_not_allowed"` |
| слишком большой контекст/файл | `413` |
Формат `error` — как у OpenAI/OpenRouter, чтобы клиент показал `message`.

### 5.5. Логирование и безопасность
- Не логировать тела запросов/ответов и значения ПДн; логировать только метаданные
  (типы и число сущностей, длительность, код ошибки).
- `PII_SERVICE_TOKEN` только в `.env`, не в репозитории.
- Проверить, что провайдер OpenRouter не получает исходные данные ни через кэш, ни через
  логи/трассировку шлюза.

## 6. Изменения в клиенте officevega (repo `getoffice`)

1. **Заголовок сессии** `X-Vega-Session: <id разговора>` — добавлять к запросам на
   `api.vega.chat` в `packages/ai-provider/src/protocols/openai-compatible.ts` и
   media-запросам (`packages/ai-provider/src/media.ts`, `media-protocols.ts`).
   Id разговора генерировать на стороне приложения (стабилен в рамках одного чата/документа).
2. **UI**: индикатор «Персональные данные обезличиваются автоматически» и обработка
   кодов ошибок из 5.4 (`pii_unavailable`, `pii_image_no_text`,
   `pii_attachment_not_allowed`) с понятным сообщением по-русски.
3. **Обход через сторонних провайдеров**: пользователь может указать собственный ключ и
   ходить напрямую в OpenAI/Anthropic/Gemini/DashScope/Zhipu/xAI и др. (`providers`,
   `media.ts`) — шлюз этого не видит. Для российской сборки/режима: отключить этих
   провайдеров или показать предупреждение о трансграничной передаче.
4. **Прочий трафик к api.vega.chat**: `packages/ai-search/src/officevega-auth.ts`,
   `apps/shell/src/main/file-index/jev.ts`, `ai-search` — проверить, что содержимое
   документов туда не уходит; если уходит — покрыть той же политикой.
5. Клиент **не** должен сам анонимизировать (pii-service тяжёлый и доступен только на
   сервере) и **не** должен слать данные не через api.vega.chat.

## 7. Критерии приёмки

1. Запрос `chat/completions` с ФИО, телефоном, паспортом в `user`, `tool`, `system` и
   `assistant.tool_calls.arguments` — на стороне OpenRouter (проверить логом шлюза на
   уровне «исходящий payload» в тестовом режиме) содержит только токены.
2. Ответ модели с токенами (JSON и SSE) доходит до клиента с реальными значениями;
   токен, разорванный между SSE-чанками, восстанавливается корректно; JSON в
   `tool_calls.arguments` остаётся валидным.
3. Один человек в разных ходах сессии и в разных падежах = один токен; разные сессии
   и разные API-ключи не пересекаются.
4. Картинка с текстом → OCR → обезличенный текст; фото без текста → `422`;
   видео/аудио → `400`.
5. `pm2 stop pii-service` → все защищаемые запросы отвечают `503`, ничего не уходит
   наружу.
6. В логах нет значений ПДн и тел запросов.
7. Задержка: добавка шлюза на типичный ход агента (≈50–100 КБ контекста, с кэшем) —
   не более ~1–2 с; повторные ходы дешевле за счёт кэша.
8. pytest для `pii-service` (session_id, restore, TTL, изоляция) и интеграционные
   тесты шлюза (JSON, SSE с разрывом токена, tool_calls, fail-closed) зелёные.
9. Клиент officevega: заголовок `X-Vega-Session` отправляется; коды ошибок из 5.4
   показываются пользователю; прямые сторонние провайдеры отключены/помечены в
   российском режиме. Тесты: `../../node_modules/.bin/vitest run` в `packages/ai-provider`.

## 8. Известные ограничения (зафиксировать в документации)

- Over-masking: слова с заглавной буквы («Москва») могут маскироваться как PERSON.
- Восстанавливается каноническая форма значения, падеж может не совпасть с исходным
  (например, «Иванову» → «Иванов»).
- Токены, которые модель исказила (изменила регистр/номер), не восстанавливаются.
- Правка документа по тексту, содержащему ПДн, работает только пока живёт словарь
  сессии (TTL); после истечения нужно перечитывать документ.
- Фото без текста не отправляются в vision-модели (нельзя замазать лица).

## 9. Порядок работ

1. `pii-service`: `session_id`, словарь, `/v1/restore-text`, тесты.
2. Шлюз: анонимизация входящих сообщений (текст, tool, tool_calls, картинки), fail-closed.
3. Шлюз: restore в JSON и SSE (с буфером разорванных токенов).
4. Клиент: `X-Vega-Session`, обработка ошибок, UI, ограничение сторонних провайдеров.
5. Интеграционные тесты, нагрузочный прогон агентного цикла, проверка логов на ПДн.
6. Выкатка: сначала `pii-service`, потом шлюз (за флагом `PII_SHIELD_ENABLED`),
   затем клиент.
